### The five cross-cutting patterns

1. **The last mile is UI wiring, not server code.** Every subapp shows the same signature: endpoints built, tested, documented in MANUAL/runbook — and never called by any frontend file. The orphan lists cross-reference each other: NexFiremap's orphaned `auth/providers` is NexIngest's missing OIDC button; NexIncidentCommand's orphaned `watch`/`links`/`merge-packages` endpoints are its own missing panels.
2. **The protective loops are computed but silent.** Unit-in-hazard and modelled-arrival warnings (safety.py) and AOI-watch hits are implemented, tested — and written only to an audit log no screen displays. Likewise the propagation model's operator-facing `caveats` ("run assumes calm…") never render. The most safety-relevant code in the product currently talks to nobody.
3. **Documentation runs ahead of the UI in exactly two places, behind it in many.** MANUAL documents two affordances that don't exist ("Position feeds" panel, drone "suggest corners" button); meanwhile genuinely implemented extras (spread-over-time topology, footprint ellipses, 16-direction solver, control-lines-as-barriers) appear in no plan document.
4. **Configuration shipped untested against reality.** Three of four bundled CAP presets cannot be parsed by the poller they configure (DWD = `.zip`, MoWaS = JSON, NWS = GeoJSON-by-default); the setup wizard probes six data sources but not Overpass/Terrarium/Nominatim.
5. **Test coverage mirrors the same split.** Manager/store layers have dedicated suites throughout; the HTTP layer and the frontend workflows are the thin spots (geocode.py wholly untested; several core GETs untested at route level; one pleasant inverse — the "unchecked" E2E browser-interaction release gate is actually largely implemented in `tests/test_browser_workflows.py`).

### Consolidated top 10 gaps (by operator impact)

1. **Surface the safety loop**: render unit-hazard/arrival warnings and AOI-watch hits; poll `GET /api/operations/watch` (README already claims this works). *(IncidentCommand)*
2. **Render model `caveats` + fix the stale "isotropic" legend text** — two small frontend changes that close the biggest honesty gap in the analytics. *(EventView)*
3. **Admin UI for integrations** — layers, CAD webhooks, position feeds (token create/rotate), OsmAnd setup; everything is curl-only today. *(Ingest + IncidentCommand)*
4. **OIDC login button** — backend flow complete and tested on both sides; the dialog is password-only. *(Firemap + Ingest)*
5. **Fix the CAP presets** (zip/JSON handling or preset replacement) so the four bundled feeds actually ingest. *(Ingest)*
6. **Map-pack lifecycle UI** — list/re-verify/retire beyond the current session (TILE_CACHE_PLAN item 5 is API-only today). *(Firemap)*
7. **Typed links + `assigned_resource_ids` authoring in the UI** — until then the Phase-4 plan-consistency warnings fire wrongly (escape routes always warn). *(IncidentCommand)*
8. **Merge resolver side-by-side view + staged-package recovery after reload** (`GET /merge-packages` is orphaned). *(IncidentCommand)*
9. **DELETE route for imported offline basemaps** — the one true backend gap on the platform. *(Firemap)*
10. **The two big analytical ambitions**: per-cell tri-state observation model (further_plan §2) and perimeter-based validation metrics (§11 gate) — real work, correctly deferred, but they are the distance between ~80% and "done" for EventView. *(EventView)*

## NexFiremap (map platform)

### Verdict

**Completeness: ~90% (47 of 52 promised items COMPLETE, 5 PARTIAL, 0 MISSING).** The map platform is substantially finished: every backend capability promised for detections, the FIRMS cache pipeline, tile proxy/cache/pinning, map packs, offline source import, coverage, EUMETSAT, jobs, backups and LAN security exists, is wired to a route, and — with the exceptions below — is exercised by a standalone test. ### Orphans and broken wiring

1. **`caveats` never rendered (orphaned operator-safety feature).** `run_propagation` and `run_ensemble_assimilation` both return a `caveats` list written expressly "for the operator rather than the log" (terrain.py:131-156, 792, 1051) — e.g. "the run assumes calm. Real wind would spread the fire faster and further downwind than shown." No file under `nexfiremap/static/` references `caveats` (grep: zero matches). The exact failure the field exists to prevent — a silently-optimistic forecast — is still invisible in the UI. Backend tested (test_terrain.test_model_caveats_name_missing_inputs); frontend wiring missing.
2. **Stale "isotropic solve" status text.** app.js:3095 tells the operator "wind/slope affect speed, not direction (isotropic solve)" in spread mode, but the solver has been anisotropic since the terrain.py rewrite (module docstring lines 7-9; README:357 says "solved **anisotropically**"). The UI now under-claims and mis-describes the served model; a crew reading it would wrongly discount directional spread.
3. **`NoWindNoSlope.base_fireline_intensity_btu_ft_s` is dead surface** (rothermel.py:151-152, 264): computed per fuel model, consumed nowhere (its FM purpose — crown initiation — is out of scope). Harmless but misleadingly present in the result object.
4. **`day_night_ratio` computed but unused** (industrial.py:396): part of the promised radiometric fingerprint, gathered by `persistence_features` and then ignored by `score_source`.
5. **Ensemble member count mismatch (cosmetic, documented):** UI button says and posts "~40 members" (app.js:2727, 2883), backend default is 60 (terrain.py:831); MANUAL:541-542 notes both. Harmless because the UI always passes 40 explicitly, but the button label and the module constant disagree about the product's default.
6. **`impact_surface.npz` from `run_propagation` stores median=earliest=latest as three identical arrays** (terrain.py:770-776). Consumers (structures exposure, safety withdrawal-on-earliest) work correctly, but the "earliest/median/latest band, never one number" README rule (README:420) is only genuinely a band for ensemble runs — the deterministic run's band is degenerate by construction and nothing labels it as such downstream.
7. **Kind-name asymmetry:** the validation job registers as `validate_event` while every sibling uses the `run_`/`analyze_`/`scan_` verb of its function; the audit-facing docs (MANUAL:1174) list it correctly, so this is cosmetic — noted only because external tooling grepping for `run_validation` as a kind will find nothing.

No orphan endpoints were found: every route in the territory has a frontend caller, and every frontend fetch targets an existing route (including `/api/jobs/{id}/files/{name}` for all result files).

### Top gaps

1. **Backend caveats never reach the operator (wiring defect, high impact, small fix).** The one mechanism that distinguishes "calm day" from "no wind data — this forecast is optimistic" is produced and tested server-side but invisible in the UI (Orphans #1). Under the project's own "we did not ask ≠ nothing there" rule, this is the most operationally consequential gap in the territory.
2. **Stale "isotropic solve" UI label actively misinforms** (Orphans #2) — one string fix, but until then the spread layer's own legend contradicts the model's actual (and correct) directional behaviour.
3. **Tri-state model is AOI-scalar, not per-cell (FP §2, the doc's "#1 highest-value accuracy improvement").** One suppression factor for the whole raster, from swath geometry + a single-point cloud sample; no L2 fire masks, no per-pixel unknown map, no interval-censored arrival. The absence is documented and partially unavoidable (no free per-pixel mask source reached), but it is the largest distance between the promised reconstruction and the shipped one.
4. **Validation cannot yet prove the model "beats the baselines" in the doc's sense (FP §11).** Without reference perimeters there is no true IoU/boundary-distance/area-bias/calibration, the physics model is not in the comparison loop, and validation runs per-event rather than over a curated historical archive — so the §11 gate ("do not proceed unless it reliably beats these baselines") is exercised but not yet satisfiable as designed.
5. **Industrial classifier depth vs the doc's design (FP ind. §§4-6, 10):** no temporal fingerprint, no footprint-intersection matching, no EEA registry, no classifier validation set, persistence capped at 30 days by design, day/night ratio collected but unused. The precision-first core (occupancy denominator, per-sensor stationarity, wildfire override, never-delete) is solid; the discriminating features that would reduce both false suppression and false alarms around industry are the missing half. Honourable mention: per-pixel moisture conditioning (FM secs 45-46) is the least-documented absence in the fire-behaviour stack.

### Orphans and broken wiring

1. **`/api/auth/providers` has no consumer.** It exists precisely to let a login screen render an SSO button; no frontend file references it, and the sign-in dialog (`index.html:27–36`) is password-only. Consequence: a configured OIDC provider is reachable only by hand-typing `/auth/oidc/login`. Contradicts `INCIDENT_LAN_RUNBOOK.md:71`.
2. **Three of four CAP presets point at non-CAP-XML representations** (`config.py:82–97`): DWD `.zip` archive, MoWaS `mapData.json`, NWS GeoJSON-by-default. `AlertManager._poll_feed` has no ZIP or JSON handling, so these degrade to "unrecognised feed format" (`alerts.py:245–246`) on every cycle — visible only in `/api/alerts/status`. Tests exercise synthetic XML only; no test covers the preset URLs' actual formats.
3. **`layers.probe` picker UI never built** — the stated purpose of the probe endpoint (`layers.py:408–416`, `routes/layers.py:49–55`) has no frontend counterpart.
4. **`MANUAL.html:354` cross-reference bug** — cites "chapter 8.5" (field observation import) for adding WMS/WMTS/XYZ layers; layer administration is actually ch. 11.4.9 API material.
5. **`cot_accept_features` without `cot_incident_id` silently drops all features** (`cot_gateway.py:300–302`) — no warning is logged and no status field distinguishes "features disabled" from "features misconfigured"; `status()` doesn't expose `cot_incident_id`.
6. Minor: `webhook_deadletter` rows are keyed to hooks and cleaned on hook delete (`webhooks.py:183`) — no orphan risk found; telemetry ingest path clean.

### Top gaps

Ranked by what would actually block a fire department's IT team:

1. **No admin UI for the entire integration surface** (layers, webhooks, position feeds). Registering a Kreis-GIS WMS layer, a CAD webhook mapping, or a vehicle feed token requires hand-crafted authenticated API calls with CSRF headers. The probe endpoint and the dead-letter/suggested-paths loop were both built *for* a UI that doesn't exist. This is the single largest promised-vs-delivered delta.
2. **CAP presets that don't parse.** The one-word configuration path the README advertises (`dwd`, `mowas`, `nws`) very likely yields zero warnings, silently except for a status field. Needs ZIP unwrapping (DWD), a MoWaS JSON adapter or corrected URL, and content negotiation for NWS (`Accept: application/atom+xml`).
3. **OIDC login unreachable from the UI.** Agency SSO is fully implemented and tested server-side but a user cannot start it from the login screen; the runbook documents a button that isn't there.
4. **CoT out is HTTP-poll only.** Real ATAK/WinTAK clients consume streaming connections or data packages, not a polled XML URL; without push over the existing TCP gateway (or TLS federation), "visible to every team already carrying TAK devices" holds for inbound only. Documented as deliberate, but it is the gap a TAK-equipped department hits first.
5. **CAP geocode-only alerts cannot be drawn** — no WARNCELLID/SAME/FIPS boundary tables (explicitly declined, `cap.py:170–176`). For German MoWaS warnings, geocode-only is common, so the warnings layer under-draws precisely in the flagship locale; the honest `without_geometry` list mitigates but does not solve it.

Dead/orphaned surface summary: `/api/auth/providers` (no consumer), probe-picker intent (no UI), 3 CAP preset URLs (wrong format), MANUAL 4.4→8.5 cross-reference, silent `cot_accept_features` misconfiguration mode.

## Live web UI observation

Driven hands-on in a browser against a fresh server instance (`--port 8010`) on the working tree, 2026-08-15, with the repo's real dev database (27k cached detections, main test fire in the Eifel region around 50.7N 6.4E). Six scripted scenarios; findings below are what actually happened on screen, not what the code implies. Viewport for most of the session: 740×910 (tablet-portrait).

### What demonstrably works well, live

- **The four-subapplication structure is real and shipped.** The title-bar app switcher lists exactly NexFiremap ("Satellite fire detections, coverage, sources"), NexIncidentCommand ("Plans, tactics, safety, resources, products"), NexIngest ("Telemetry, drone imagery, field data, imports"), NexEventView ("Fire event detection and behaviour analysis"), and switching swaps the side panel content coherently.
- **The signature interaction works end-to-end.** Right-click on the fire → menu offers *Copy coordinates / What's here / Zoom in here / Situation here / Create incident here*. "Create incident here" produced, in one click: a reverse-geocoded incident ("Wildfire near Märchenwald Altenberg"), a first operational period, a "Plan A · primary" scenario, and an AOI — confirmed server-side, with a toast explaining exactly what was created.
- **Situation-at-point renders every provider honestly.** One right-click answered: detections 12.6 h ago; event 1 (311 detections, last seen 18.6 h); two nearby active incidents by name; "no completed propagation run available"; structures "none scanned within 5 km"; units "no tracked positions"; **next overpass TERRA (MODIS) in ~4.4 h**. Unavailable ≠ silent, exactly as designed.
- **The corrected Spread-over-Time encoding is live**: nested cumulative bands render dark-core → orange → purple-outer (latest = most salient), with the legend showing real UTC timestamps ("2026-08-12 18:53 UTC → 2026-08-15 12:02 UTC") instead of vague Earlier/Later once data is loaded.
- **Cost and freshness are visible.** The cache panel live-updated during the session (14k→27k rows, API budget 32/182 of 5000 counted against the autofetch the browsing itself triggered); footer permanently shows "local server connected · cache 27K".
- **Honest layer copy.** Coverage ("was this area even watched, not was it seen clearly"), industrial ("never deletes anything, only distinguishes"), EUMETSAT (revisit, region limits, known false-positive mode) each carry their epistemic caveats in the panel itself.
- **Responsive behavior exists**: at tablet width the side panel becomes a collapsible bottom sheet; the coordinate search's `lat, lon` shortcut works offline-safe and labels the interpretation ("read as WGS84 decimal degrees").
- **The incident-command vocabulary on screen matches doctrine**: 38 semantic tactical types (full LCES set — Lookout, Escape route, Safety zone, Trigger/decision point — plus Evacuation area, Water source, Dip site, Structure protection area) with a 12-state status vocabulary, and the workspace lists every promised section (safety review, resources, recovery/snapshot comparison, calculators, model provenance, classified products, package conflicts, verified backup with size and download link).

The fire-service needs assessment states "no PWA/service worker". ### Top wiring gaps (ranked)

1. **Safety warnings never reach an operator** (`d`). The entire geofence + modelled-arrival machinery (`safety.py`, `telemetry.py:452-502`) terminates in the audit log and the *device's* HTTP response. No panel, banner, or marker shows "L-1 is inside the forecast perimeter". Smallest fix with the largest payoff: include recent `safety_warning` audit rows in `vehicle-positions/latest` or a small poll, and render them in `operations.js`'s vehicle status line.
2. **AOI watch is computed for nobody** (`e`). `GET /api/operations/watch` was explicitly designed for the frontend refresh cycle ("the frontend passes the timestamp of its last poll", `routes/links.py:249-251`) — no frontend code polls it, and the AOI polygon itself is never drawn, so the whole "does this new detection concern anyone" answer is invisible.
3. **The event context menu is dead code** (`a`, fabric). `integration.js:151-175` ships "Attach event to ⟨incident⟩" and "Create incident from this event", plus the snapshot plumbing — unreachable because `emitMapContextMenu` is only ever called with `kind:"point"|"area"`. Either app.js's event layer should emit an event-kind menu on right-click, or this is 25 lines of illusion.
4. **Control lines never constrain the model** (`g`). `control_mask` + `CONTROL_LINE_BUILT` (`safety.py:328-398`) and `terrain.build_directional_behavior(control_lines=…)` exist and are unit-tested — and no propagation path connects them; `POST /api/events/{id}/propagate` doesn't even accept an incident id. The carefully-argued "a planned line must not flatter the plan" rule protects a code path that doesn't run.
5. **Model-run attach is a typed job ID** (`b`). app.js publishes the active analysis's `jobId` on the bus; operations.js ignores it and asks the operator to transcribe a number (`operations.js:1321`) — the exact "operator retyping" failure mode the integration layer exists to remove.
6. **No model-geometry adoption** (`c`). Isochrones/envelopes cannot become `forecast_perimeter`/`trigger_point` features except by hand-tracing, even though the tactics screener and the safety geofence both consume those feature types.
7. **CAP alerts and structures are read-only islands** (`h`, `i`). Both have link kinds reserved (`alert`, `structure`) and neither has any producer or context-menu action; the operational half cannot record "this incident responds to that warning" or "protect this building" without free-hand work.
8. **Links are write-only in the UI** (`k`). Everything attached to an incident lands in `incident_links` with a frozen snapshot and travels in exports — but no screen lists an incident's links, so "what is this incident based on" is answerable only by reading JSON.
9. **Safety ignores model staleness** (`l`). `_active_arrival` takes the newest `model_run` link unconditionally (`safety.py:132-135`) while the wind module and the scenario panel both track `is_stale` — the one consumer where staleness is life-safety-relevant is the one that doesn't check.
10. **Dead bus surface**: `onActiveTool` and `getMap` exports with zero consumers (`context.js:49,220`) — trivial, but they misstate the fabric's real shape.

# NexFiremap — domain needs assessment (fire-service doctrine as the yardstick)

## Fire-service needs assessment

Reference frame: ICS/NIMS practice (ICS-201/204/205/214, T-cards, operational periods), wildland doctrine (LCES, 18 Watch-Out Situations, trigger points), dispatcher/CAD workflow (status keeping, AVL, premise info), and German/European civil protection (FwDV 100 Führungssystem, DV 102 Taktische Zeichen, MoWaS/NINA/DWD warning chain — relevant because the app ships DWD/MoWaS CAP presets and a DV 102 symbology profile). The catalog below was built from that doctrine first, then graded against the code.

### Verdict

NexFiremap is unusually strong exactly where most mapping tools are weak: LCES is first-class vocabulary, the fire-behaviour model is wired to protect people (`safety.py` evaluates every unit position against the arrival raster), the situation query answers "how long have I got" at a point, the audit trail is transactional, products cover IAP/briefing/evacuation/handover in ten templates, and symbology honestly supports DV 102, ICS/NFPA 170 and a neutral profile. It is a genuine common operating picture for a planning cell on a laptop.

Where it falls short of doctrine is the *tempo* end and the *field* end: dispatcher status-keeping is a five-value vocabulary without the enroute/on-scene distinctions every CAD uses; there is no MAYDAY affordance anywhere; a firefighter on a phone can send a position but cannot see their assignment; trigger points exist as dots but are never evaluated against the model that could give them meaning; there is no exercise mode, so every drill pollutes the operational record; and the warning chain is one-way — CAP flows in from DWD/MoWaS, nothing flows back out toward the population.

Grading: 14 COVERED, 17 PARTIAL, 5 ABSENT across 36 cataloged needs.

### Top-10 roadmap (frequency of need × severity when missing)

1. **MAYDAY/emergency path** — structural-lite. Accept CoT emergency atoms and add a field-side panic endpoint; render as a modal, sound-on alarm on the COP with LKP + nearest units (reuse `situation.py:278`). Rare event, catastrophic gap; partial quick win because ingest and nearest-unit machinery already exist.
2. **Expanded unit-status workflow** — quick win. Add `dispatched`/`enroute`/`on_scene` (FMS 3/4) to `RESOURCE_STATUSES` (`vocab.py:68`) plus a status-timestamp column and a one-tap status bar; audit already gives history for free. Used every minute of every incident.
3. **Standing fireground weather widget** — quick win. The Open-Meteo fetch in `terrain.py` already returns T/RH/wind; surface it (with trend and forecast hours) in a persistent panel and stamp it on the safety checklist's "weather update is current" item. Constant-frequency need, moderate severity.
4. **Trigger-point ↔ model evaluation** — quick win on existing rails. Evaluate every `trigger_point` against the cached arrival raster (`safety.py` already caches it per job) and show "modelled fire arrival at TP-2: 1.4–2.6 h"; warn when a re-run shortens it. This is what makes LCES support real rather than decorative.
5. **ICS-214 activity log + ICS-205 comms table** — quick-to-medium. A free-text, append-only journal entity per incident (the audit-trail pattern in `operations/audit.py` is the template) and a channel-plan table rendered into the briefing product. Every incident, legal significance.
6. **Water-source/hydrant Overpass scan** — quick win. Clone the `structures.py` scan pattern for `emergency=fire_hydrant`/`water_source` tags into a cached layer. High frequency (every structure-threat fire), cheap.
7. **Crew mobile view ("my assignment")** — structural. Bind accounts to resources, serve a stripped read-mostly view (my task, my division, nearest safety zone, MAYDAY button) with large touch targets; pairs with QR-code enrollment for position feeds to kill the token-hand-typing friction (`MANUAL.html:748-751`).
8. **Exercise mode** — medium. An `exercise` flag on incidents propagated to products (banner), watch/safety evaluations (labelled), and a purge path; mirrors how `ingest/cap.py:53` already treats non-`Actual` CAP statuses. Weekly-frequency need for any agency that trains.
9. **Outbound CAP authoring** — medium. Draft a CAP-XML export from an `evacuation_area` polygon (the inverse of `ingest/cap.py`) so the MoWaS/NINA request is an attachment, not a phone description. Low frequency, very high severity.
10. **PWA/offline shell + delta sync** — structural. Service worker caching the SPA and tiles from map packs, plus delta polling, so a phone that drops off the LAN degrades to a cached map instead of a dead page. Prerequisite plumbing for item 7.
