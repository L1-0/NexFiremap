NexFiremap Manual

Covers all four Nex modules: NexFiremap, NexEventView, NexIncidentCommand and NexIngest.

This manual documents the NexFiremap application as implemented in this repository. It is written for two audiences in one document: operational staff who use the map and incident-command tools, and developers or administrators who install the server, call its API, or deploy it on an incident LAN. Chapters 1 to 9 describe what the application does and how to use it from the browser. Chapter 10 is a configuration reference. Chapter 11 is the developer guide: API endpoints, data formats, and how to set up network routing for shared use. Chapter 12 is a glossary and appendix.

Accuracy note. Every endpoint path, field name, default value and status label in this manual was read directly from the source code in this repository at the time of writing, not inferred from marketing text. Where the software itself states a limitation or a simplification, this manual repeats it rather than smoothing it over. If code and manual ever disagree, the code is correct; report the mismatch so this manual can be corrected.

Status. NexFiremap is a locally run research and planning tool, not a certified dispatch or life-safety system. The project's own completion ledger (END_TO_END_TODO.md) marks a number of items as complete in code while leaving external gates open: hardware drills, brigade exercises, dependency security scans and formal certification. Treat every model output, warning and calculator result as decision support that a qualified human must review, not as an automated determination.

1. Introduction

NexFiremap is a locally run server that overlays NASA FIRMS active-fire satellite detections on a choice of OpenStreetMap-based basemaps, with a rolling local cache so that history stays available without re-downloading it. Beyond the base map, the same server hosts three further tools: fire event detection and behaviour modelling, an offline incident-command workspace, and a set of ingest tools for telemetry, drone imagery and field data. All four are described in this manual as the four Nex modules (chapter 4).

1.1 Design principles

These principles are implemented in the code, not just stated as intent:

  • Observed, Estimated, Modelled and Uncertainty are kept separate. A raw satellite detection, a statistical likelihood estimate, a physics-based spread model and its uncertainty band are never merged into one number. Each layer says what kind of information it is.
  • No machine learning. Every analysis layer uses classical statistics, geostatistics or physics (kernel density, inverse-distance weighting, the Rothermel fire-spread equation, rule-based scoring). This is a deliberate project choice, stated in the source, not a limitation of the current version.
  • Computation happens locally. All analysis runs on the machine running the server. Nothing is uploaded to a third party for processing.
  • Expensive work runs in the background at low priority. Clustering, rasters, imagery and physics models run as separate operating-system processes dropped to idle priority, so they do not compete with anything else running on the same machine (chapter 11.3).
  • Every data source except FIRMS is free and keyless. Celestrak, Microsoft Planetary Computer, Open-Meteo, OpenStreetMap Overpass, AWS Open Data terrain tiles and Nominatim require no account. Only NASA FIRMS requires a free registration (chapter 2.3). EUMETSAT is an optional additional source that does require its own free account (chapter 5.7).
  • Nothing is silently deleted. Classifying a detection as industrial, superseding a plan, or importing an update never removes the original record. Superseded or flagged data stays available, just labelled.

1.2 What is and is not included

NexFiremap displays satellite-derived fire detections and research-grade estimates of extent and spread. It is not an authoritative fire-behaviour product, not a certified dispatch system, and not an automated safety determination. Every screen that produces a warning, a calculated value or a model output says so in its own text, and this manual repeats those statements rather than removing them.

2. Installation and first start

2.1 Requirements

NexFiremap runs on Windows, macOS or Linux. It needs Python and an internet connection for installation and for fetching live data (the map itself keeps working offline once data is cached; see chapter 8.4 for offline area preparation). No database server, no external services beyond the free sources listed in chapter 1.3, and no CDN calls: fonts, mapping libraries and icons are bundled in the repository.

2.2 Installing

The setup wizard is the recommended install path. It creates a Python virtual environment, installs dependencies, asks for the FIRMS map key, and tests reachability of every data source before the server is ever started.

On macOS or Linux, if double-clicking does not work the first time, run chmod +x install.sh install.command start.sh start.command once, or run bash install.sh directly. The wizard sets the executable bit on the other launchers afterward. The wizard is also runnable directly as python scripts/setup_wizard.py, and is safe to re-run at any time, for example to add a key later or re-check connectivity. It reuses the existing virtual environment and never overwrites a setting that has already been changed.

To install without the wizard:

python -m pip install -r requirements.txt
copy .env.example .env
notepad .env    # paste your FIRMS_MAP_KEY
python run.py --open

(On macOS or Linux, use cp and a text editor of choice instead of copy and notepad.)

2.3 Getting a FIRMS map key

NASA FIRMS requires a free key to use its web services. Request one at firms.modaps.eosdis.nasa.gov/api/map_key. Without a key the map still loads, basemaps and the interface work, but no fire detections can be downloaded. A banner in the interface explains this until FIRMS_MAP_KEY is set in .env and the server is restarted. The event-analysis, incident-command and ingest tools do not need this key; only the raw satellite-detection layer does.

2.4 Starting the server

Either the wizard or the manual steps end the same way: open http://127.0.0.1:8000 once the server is running (the --open flag, or the wizard, does this automatically). The default port is 8000 and can be changed with NEXFIREMAP_PORT (chapter 10).

By default the server binds to the local loopback address only, so it is reachable from the same machine and not from other devices on a network. Sharing it with other devices on an incident LAN is a deliberate, separate step covered in chapter 11.6, because it changes the security model: an explicit LAN mode, TLS and named accounts are all required before the server will accept non-loopback connections.

2.5 Graceful degradation

The event-analysis modules (orbits, events, likelihood, imagery, terrain and their dependents) pull in optional packages, and rasterio in particular has platform-specific install friction. If one of these fails to install, the server still starts and the core fire map still works: the affected feature reports itself unavailable through GET /api/config's features field, and its buttons disable themselves in the interface with an explanation instead of the application crashing. The setup wizard's package-by-package fallback and connectivity tests exist to catch this before the map is ever opened.

3. Signing in, accounts and roles

3.1 Two modes

By default NexFiremap runs with no login screen at all: it only listens on the local loopback address, so only the same machine can reach it, and authentication is not required. This is the mode described in chapter 2.

Setting NEXFIREMAP_LAN_MODE=true switches to a fail-closed, authenticated mode intended for sharing the server with other devices on an incident LAN (chapter 11.6). In this mode every browser sees an "Incident LAN sign in" dialog before anything else loads, and every API request must belong to a signed-in session. There is no in-between state: the server either trusts anyone who can reach it (loopback default) or requires a named account for everyone (LAN mode).

3.2 The built-in administrator account

When LAN mode is enabled, the server requires NEXFIREMAP_ADMIN_PASSWORD to be at least 12 characters, or it refuses to start. On every startup it creates or updates a local account named admin with the role administrator and that password. This means the admin password is always whatever is currently set in the environment: if it is lost, an administrator stops the server, sets a new NEXFIREMAP_ADMIN_PASSWORD, and restarts. This rotates the password without deleting any incident data. Record any emergency password change in the incident log.

3.3 Roles

There are six roles. A role is fixed per account; there is no per-object permission editing beyond role membership.

The Public incident information panel is what a public-role account sees: only products explicitly generated with the public-information template (chapter 7.8) appear there. Nothing else in the incident workspace is reachable by that role, by server-side check, not just by hiding the button in the interface.

3.4 Creating accounts

Only an administrator can create accounts, from Incident LAN accounts under the NexIncidentCommand module (this section is hidden from every other role). Enter a username, choose a role, and set an initial password of at least 12 characters. Issue each person their own named account with the least-privileged role that covers their job; do not share the administrator account, and do not let the admin login be a routine daily login for a field user.

3.5 Sessions and login limits

A session lasts NEXFIREMAP_SESSION_MINUTES (default 30) from login, holds a session token and a separate CSRF token, and is checked on every request. Login attempts are rate-limited: at most 10 attempts per 60 seconds per client. If a device cannot sign in, an administrator creates a replacement named account; do not disable authentication or fall back to loopback-only mode to work around a lockout while the server is meant to stay on the LAN.

4.3 Situation reports

Right-clicking a point on the map, or dropping a single Waypoint, can show a situation report: everything every part of the server currently knows about that point, gathered in one place. Under the hood this calls a single endpoint (chapter 11.4.7) that asks every relevant part of the server in turn: nearby detections, which fire event (if any) the point falls inside, which incidents' areas of interest cover it, a modelled arrival estimate if a spread model has been run nearby, nearby structures from a prior scan, in-force official warnings, nearby tracked vehicles, and the next satellite overpass. A part that could not answer, whether because it is not configured or because it failed, is named as not consulted rather than silently left out, so "we did not check" and "there is nothing there" are never confused with each other.

Right-clicking a detected fire event also offers attach event to (incident), when an incident is active, and create incident from this event; right-clicking empty map space offers create incident here or, with an area selected, create incident for this area. Each of these creates the incident together with its first operational period, its first scenario, and, where relevant, an area of interest and a link back to what was selected, in one step (chapter 11.4.7).

4.4 Basemap and overlays

The map-style button (bottom right of the map) opens a grid of basemaps: OpenStreetMap, Humanitarian OSM, OpenTopoMap, CyclOSM, Carto Positron (light), Carto Dark Matter, Esri World Imagery, and Esri Terrain (full detail to zoom 9, enlarged beyond that). A place-labels overlay can be switched on over any of them. An administrator can add further WMS, WMTS or plain XYZ layers from an external service (layer administration, chapter 11.4.9), or an imported local MBTiles/GeoTIFF basemap (chapter 8.4); both then appear in this same picker.

4.5 Search and coordinates

The search box in the top bar resolves place names through a server-proxied, cached, rate-limited call to Nominatim, or jumps straight to a typed coordinate pair with no network call at all, so that shortcut still works with the wide-area network down. A format selector next to it controls both how typed coordinates are parsed and how coordinates are displayed elsewhere in the application: WGS84 in decimal degrees, degrees/minutes/seconds, or degrees/decimal minutes; UTM; MGRS; British National Grid; Irish Grid; Swiss CH1903+/LV95; French Lambert-93; Dutch RD New; New Zealand Transverse Mercator; Sweden SWEREF99 TM; Australia GDA2020 MGA (zone chosen automatically); or a custom EPSG code or proj4 string. This is a shared, server-remembered preference for the whole installation, not a per-browser setting, so a room of operators sees the same coordinate format by default (chapter 10, Settings).

4.6 Other shared controls

Print this view opens a print-formatted version of the current map (and, inside NexIncidentCommand, the current operations record via print operations map, chapter 7.12). The panel toggle (hamburger icon) shows or hides the side panel. The connectivity and cache pills at the bottom of the panel show whether the local server is reachable and how much is cached. In LAN mode, the identity pill and sign out button appear next to them (chapter 3).

4.7 Official warnings

When one or more Common Alerting Protocol (CAP) feeds are configured (chapter 10.10), a small control in the bottom right of the map offers an Official warnings checkbox. Turning it on draws official public warnings (for example a national weather or civil-protection feed) as dashed, lightly filled polygons, styled by severity, distinct in appearance from anything NexFiremap itself analyses, since these are unmodified third-party warnings shown for context, not a NexFiremap output. Each warning's popup links to the original source document. Warnings with no mappable area (a geocode the server does not have a boundary for) are counted separately rather than silently dropped. This control does not appear at all if no feed is configured.

5. NexFiremap: satellite fire detections

NexFiremap is the default module: raw satellite fire detections on a basemap, with the tools to filter, style and cache them. Switch to it from the module menu in the top left. Its panel starts collapsed; open it with the panel toggle button (the hamburger icon, top right) or by switching to any other module, which opens the panel automatically.

5.1 Time window and history

Time window offers 24h, 3d, 7d, 14d or 30d buttons. Older data is served straight from the local cache, so widening the window after the first load is usually instant. Detections per day draws a small histogram; click a bar to isolate that day, click clear day filter to return to the full window. Acquisition-time playback adds a play/pause control and a time slider that reveals detections in the order satellites actually recorded them, rather than all at once.

5.2 Display

Colour by chooses what the detection colour encodes: detection age, fire radiative power (FRP), or instrument. Render as chooses how detections draw: individual points, clustered markers, or a heatmap. A legend below explains the current colour scale.

5.3 Filters

Satellites lists the configured FIRMS sources (VIIRS NOAA-20, VIIRS NOAA-21, VIIRS Suomi-NPP, MODIS Aqua/Terra, and Landsat where available) as checkboxes. Confidence filters low/nominal/high. Minimum FRP is a slider in megawatts. Overpass restricts to daytime-only or night-time-only detections.

5.4 Satellite coverage

Toggling show under Satellite coverage draws a grid of cells shaded by how recently a tracked satellite's orbit actually passed over each area, brighter meaning more recent. This is computed from real orbit propagation (Celestrak two-line elements, propagated with Skyfield) as a geometric approximation: a circle of each sensor's nominal half-swath width swept along its ground track, not the true bow-tie-shaped scan, and not checked against cloud cover. It answers "could a satellite have seen this spot", not "did it see this spot clearly". Five satellites are tracked: NOAA-20, NOAA-21, Suomi-NPP (all VIIRS), and Terra and Aqua (both MODIS).

5.5 Industrial and static sources

Recurring non-wildfire heat, such as flares, kilns, refineries and power plants, is identified from OpenStreetMap tags plus this server's own cached detection history, never by deleting anything, only by labelling. Turning on show scans the current view automatically for small or medium areas; use rescan now to force a refresh or to check a large area on purpose. The scan looks for OpenStreetMap tags such as flares, kilns, refineries and power plants (excluding tags the classifier's own design notes call unreliable, like generic industrial land use or substations), scores each candidate against how many distinct days had a nearby detection, how tightly clustered those detections are, and how consistent their radiative power is, and labels each candidate one of:

  • persistent_industrial: strong, precision-first evidence this is a recurring non-wildfire heat source.
  • ambiguous: some evidence, not enough to suppress with confidence.
  • insufficient_evidence: not enough cached history yet to say either way.
  • possible_industrial_incident: a source that was previously classified persistent but whose nearby detections have since grown well beyond its usual footprint, downgraded so a real fire at an industrial site is not hidden.

Because the server only ever retains a rolling window of history (30 days by default), this classification reflects that recent window, not years of behaviour. Treat "insufficient evidence" as genuinely undecided, not as "probably not industrial".

5.6 EUMETSAT confirmation (optional)

This panel only appears once EUMETSAT_CONSUMER_KEY and EUMETSAT_CONSUMER_SECRET are set (chapter 2.3, chapter 10.10). It draws an independent geostationary active-fire signal from EUMETSAT's MTG/FCI instrument, about every 10 minutes, covering Europe, Africa, the Atlantic and the Middle East only (roughly 67.5 degrees north/south of the equator). It reports a fire-confidence classification and probability per pixel, not a radiative-power value the way FIRMS does, so treat it as a second, independently-sourced yes/no confirmation rather than a magnitude cross-check. A known false-positive mode is low-confidence hits over water from sun glint.

5.7 Cache

Cache this view for 30 days explicitly warms the cache for the current viewport. Refresh newest data re-checks the hot (most recent) days for everywhere already cached. The panel below shows cache size and related figures; the connectivity and cache pills at the bottom of the side panel summarise local server and cache health at a glance. See chapter 9.1 for how the cache pipeline works underneath these buttons.

6. NexEventView: fire event detection and behaviour analysis

NexEventView groups raw detections into discrete fires and offers a progressively heavier set of analysis layers on top of a selected fire. Every layer here is a research-grade estimate. Each says what kind of information it is (Observed, Estimated, Modelled, or Uncertainty), and none is a substitute for a qualified fire-behaviour analyst's judgement.

6.1 Detecting events

Click find in view to group cached detections in the current viewport into distinct fires. This is not a bounding box: it is a space-time graph. Two detections are linked if the distance between them is within the sum of their sensor footprint radii plus an assumed maximum fire growth speed (8 km/h by default) times the time between them, and within a maximum time gap (7 days by default). Connected groups of detections become one event. A known failure mode of this kind of clustering is chaining: many individually-plausible links, for example scattered agricultural burning across a wide region, can connect detections that have nothing to do with each other into one nominal event. NexFiremap guards against this by splitting any cluster whose real span exceeds a plausible single-fire size (100 km by default, chosen with reference to the 2021 Dixie Fire, one of the largest single-ignition wildfires on record) back into smaller pieces. If a shown event is still unusually large, the panel displays an explicit warning to review the raw detections before trusting any analysis layer, since it is more likely several unrelated fires chained together than one real fire that size.

Re-running detection over an overlapping time window creates new event records rather than merging into previously found ones; this is a known limitation of the current version, not a bug.

6.2 Selecting and analyzing an event

Pick an event from the list and click analyze to unlock the layer switch (a row of buttons: Likelihood, Arrival time, Burn scar, Modelled spread, Ensemble) and the supporting tools below it. Burn scar, Modelled spread and Ensemble stay disabled until their own run has completed, since each is a separate background job.

6.3 Likelihood

An active-heat probability raster: each detection contributes a Gaussian-shaped patch centred on itself, sized to its own sensor footprint, weighted by which satellite instrument saw it, how confident the detection was, and how much radiative power it carried, then faded out over time (a configurable half-life, 6 hours by default: a detection's influence roughly halves every 6 hours as it ages). Detections are combined so that the result reads as "the probability at least one detection's evidence is still active here", not a simple sum.

A distinguishing feature of this layer is that it also uses negative evidence: if a satellite's swath genuinely passed over part of the area and recorded no detection there, that pulls the likelihood down in that area, softened by how likely the sky was actually clear at the time (from historical cloud-cover data), since a satellite pass alone cannot tell a clear sky from a cloudy one. A cell no satellite ever looked at is left untouched, never treated as confirmed clear. This is referred to elsewhere in this manual and in the application as the tri-state observation model: observed fire, observed no-fire, and never observed are three different things.

6.4 Arrival time

An inverse-distance-weighted estimate of when fire likely reached each map cell, built from every detection's own time and distance to that cell. The layer reports three figures per cell: a median estimate, and an earliest/latest spread one standard deviation either side of it. This is an honest spread, not a fabricated single precise timestamp, and not the literal earliest/latest detection times.

6.5 Uncertainty envelopes and isochrones

The uncertainty envelopes / isochrones switch overlays 50, 80 and 90 percent probability-mass contours: the smallest region that contains that fraction of the likelihood raster's total mass, drawn as filled, nested bands with an area figure in square kilometres and square miles, not an arbitrary fixed-threshold outline. For modelled spread, the same switch instead draws isochrones, lines and filled bands showing how far fire is estimated to have reached by 3, 6, 12, 24 and 48 hours, brightest for the soonest horizon and fading for the furthest.

6.6 Burn scar

Click check burn severity (Sentinel-2) to compare a pre-fire and post-fire satellite image using the normalized burn ratio (NBR) and its pre/post difference (dNBR), classified into unburned, low, moderate and high severity using standard published thresholds. Scenes are searched independently before and after the fire: Sentinel-2 first, falling back to Landsat if no sufficiently clear Sentinel-2 scene is available within the search window. Because each side is chosen independently, it is possible for one to end up Sentinel-2 and the other Landsat; when that happens the result is marked cross_sensor, since no correction is applied between their slightly different infrared channels and severity can carry a small systematic bias in that case. This layer uses actual optical imagery, not thermal inference, so it is ground truth of what burned, not a live estimate of where fire currently is.

6.7 Modelled spread

Click run spread model (terrain + weather) for a deterministic physics-based estimate of how the fire has spread and may continue to spread, using a real Rothermel (1972) surface-fire model with the Albini (1976) correction, Anderson's 13 standard fuel models, elevation and slope from the Copernicus global 30m digital elevation model, land cover from ESA WorldCover crosswalked to a fuel model, one weather sample for the area from Open-Meteo, and dead-fuel moisture conditioned from recent weather history rather than a flat assumption. Spread is solved anisotropically: fire genuinely spreads faster downwind and upslope and slower into the wind, using the standard Albini and Chase (1980) elliptical model. The result is not survey-grade: it uses one wind sample and one moisture value for the whole area (slope and aspect still locally bend the fire's own spread direction), one fuel model per land-cover class rather than a calibrated local fuel map, and does not model crown fire or spotting. These simplifications are stated directly in the application's own model documentation, not hidden.

6.8 Ensemble

Click run Monte Carlo ensemble (~40 members) (the current default is 60 members) to run many spread-model variations at once, each sampling a different plausible wind speed and direction, fuel-moisture and general spread-rate uncertainty, plus a small jitter on the ignition point. Every member is then scored against the event's own later detections (arrival time predicted by that member compared with when a detection actually occurred nearby), and members that predicted better are given more weight. The reported result is a weighted spread of outcomes (10th/50th/90th percentile arrival time per cell) using those weights, not a resampled simulation: the application's own documentation is explicit that this is a batch weighted calibration using the same evidence-reweighting idea a full particle filter is built on, not a fully recursive particle filter that re-simulates between each observation. An effective-sample-size figure is reported alongside the result so the quality of that weighting is visible rather than hidden.

6.9 Validate model

Click validate model (rolling backtest) to test how well the served likelihood model would have predicted this event's own history, compared against several simple, non-learned baselines (a static buffered footprint, a concave hull around early detections, constant-rate radial growth, and a wind-driven ellipse). The test works by hiding later detections, asking each model to predict them from only the earlier ones, then scoring precision, recall, a point-based overlap proxy, Brier score, centroid displacement, predicted area, and (for the served model only, since it is the one with a native time estimate) arrival-time error. This is the project's evidence that its estimates are not just plausible-looking, they are checked against what a satellite actually saw next.

6.10 Structures at risk over time

Once a spread or ensemble run has completed, the Structures at risk over time panel appears. Click cache / refresh buildings for model area while online to pull OpenStreetMap building footprints for the area (these stay cached in SQLite for later offline runs). Move the highlight reached within slider (0 to 48 hours) to see which structures the modelled arrival surface reaches by that horizon, and a running count split into residential buildings and critical facilities (hospitals, clinics, fire and police stations, schools, care homes, shelters). This is scenario exposure timing only. It is never a label of confirmed damage or an evacuation instruction.

6.11 3D terrain view

Click view in 3D terrain to drape whichever layer is currently on screen (likelihood, burn severity, modelled spread, ensemble) over real elevation, using free Terrarium-encoded elevation tiles over an OpenTopoMap base. This opens a second map engine (MapLibre GL JS) as a full-panel overlay; drag to orbit, scroll to zoom, shift-drag to tilt. Use the back to 2D map button to return.

7. NexIncidentCommand: plans, tactics, safety, resources, products

NexIncidentCommand is the offline incident-command workspace: incidents, operational periods, plan scenarios, tactical drawing, safety review, resources, model provenance, products and handover. It works entirely on the local server and needs no internet connection once running. Everything you record here is saved to the local SQLite database and survives a restart.

7.1 The incident hierarchy

Records nest in one fixed order: an incident contains operational periods; a period contains plan scenarios; a scenario (or the incident directly) contains tactical and observation features, the things drawn on the map. Resources (crews, engines, aircraft) belong to the incident as a whole, not to any one period or scenario. This is described in more technical terms, including exact field names, in chapter 11.4.

7.2 Creating and selecting an incident

Click new incident to create one centred on the current map view; NexFiremap creates a first 12-hour operational period and a primary scenario named "Plan A" automatically. Use the Active incident selector to switch between incidents. Once one is selected, the Operator / unit field, Operational period and Plan scenario selectors appear; almost everything else in this module acts on whichever period and scenario are currently selected. Use next period to start a fresh operational period rather than overwriting the one before it, and new scenario to add an alternative, contingency or worst-case plan alongside the primary one.

Under Incident, period and scenario records, edit the incident's name, identifier, status (active, contained, closed), timezone and notes; the period's name, status (draft, active, closed), start and end time, and objectives; and the scenario's name, kind (primary, contingency, alternative, worst case), status and description/assumptions. Editing an approved scenario's name, kind, description or assumptions returns it to draft and clears its approval, so it goes through safety review again.

8. NexIngest: telemetry, drone imagery, field data, imports

NexIngest brings outside data into an incident: live vehicle positions, wind observations, drone imagery, imported map data, field observations, and manually recorded positions. Select an incident, period and scenario first (chapter 4.1); most of this module writes into whichever incident is currently active.

8.1 Live vehicle telemetry

Automatic GPS positions are a separate, unconfirmed feed, distinct from the manual position reports and drawn tactical features described elsewhere. Click refresh positions to pull the latest known position per vehicle; tick show last two hours of tracks to draw recent history. A gray position is stale (older than the configured staleness threshold, chapter 10.6); a red position or a broken track line carries a quality warning, such as an implausible jump in speed or a report that arrived out of order. Estimated movement between two real reports is only ever a display estimate, clearly marked as such, and is never written as an observation in its own right.

An administrator sets up each vehicle's feed under Position feeds: creating one mints a one-time token that must be transferred to the vehicle's gateway through a secure channel, since it cannot be recovered afterward, only rotated. A feed sends positions to POST /api/feeds/positions/<source id> with that token; see chapter 11.7 for the exact formats accepted (native JSON, or CoT/TAK, NMEA, or MAVLink without any translation step).

8.2 Temporal wind situation

Set a situation time, a look-back window and an arrow-grid density, then click show wind for current view. Arrows point downwind (the direction air is moving toward, not the meteorological "from" direction wind observations are recorded in) and are coloured cyan under 5 m/s, amber 5 to 10 m/s, red at 10 m/s or above. Dashed rings mark actual measured points; everything else is a labelled estimate, interpolated in space from nearby observations and blended with whatever weather was already attached to a model run for the same area and time, weighted more heavily toward real observations the closer they are in space and time. This never makes a live network request: it is built entirely from wind observations already recorded (chapter 7.3, object type "wind observation") and weather already attached to a completed model run, so it works fully offline. It is not a terrain-resolved wind model.

8.3 Drone imagery desk

Create a mission (name, aircraft, operator), then upload images against it. Every original image is retained as evidence with a SHA-256 hash, whether or not it is ever georeferenced. To place an image on the map, affirm it as nadir (looking straight down) or orthorectified, and supply its four corners in order, top-left, top-right, bottom-right, bottom-left, as WGS84 coordinates. This is an operator-affirmed label, not something the software determines on its own; the placement itself is a straightforward four-corner warp of the image onto those corners, not photogrammetric bundle adjustment. suggest corners (where offered) proposes a footprint automatically from the image's own flight metadata (gimbal angle, altitude, focal length) when that metadata is present and the camera was reasonably close to looking straight down; it refuses to guess, rather than propose something wrong, whenever the image includes sky, has no usable altitude or focal length, or the metadata camera model is not one of the few verified against published specifications. A suggestion still requires the operator's own confirmation before it is used. Select a set of georeferenced frames and click mosaic selected georeferenced frames for a deterministic visual composite (overlaps resolved by a fixed rule, not colour- or seam-matched), explicitly not survey-grade orthomosaic output.

8.4 Offline AOI coverage and local map imports

Offline AOI coverage checks every tile at every whole zoom level in a chosen range against what is already on disk for the current view, and reports missing or modified files; only a result marked ready for offline use, with every zoom level complete, means the area is actually prepared. This never bulk-downloads from a public tile provider on its own, since most of their usage policies do not permit that. For deliberate all-zoom offline coverage, use Import local MBTiles / geospatial raster to validate and add an administrator-supplied MBTiles file, GeoTIFF, or raster GeoPackage, recording its source, attribution, licence, acquisition date and any limitations; it then appears alongside the built-in basemaps. Once such a source is an imported elevation model, derive slope, aspect and contours computes a terrain package entirely offline from it.

8.5 Import field observations

GeoJSON, GPX, KML, KMZ, vector GeoPackage and CSV files are parsed locally, previewed against the current map view, and only applied after review. If any imported feature falls outside the current view, applying the import requires an explicit acknowledgement; if any imported feature would be a confirmed perimeter or a confirmed status, applying it requires a written confirmation reason. An optional field mapping (JSON) tells the importer which of the source file's own column or tag names correspond to NexFiremap's fields, for example {"latitude":"lat","longitude":"lon","title":"name","observed_at": "time"}. The original uploaded file, its hash, and the import report all remain attached to the incident's handover record. Observed progression comparison shows which observations were present at the start of a chosen interval and which were added during it, useful for briefing on what has changed.

8.6 GPS / radio position report

For a position received by voice or a device with no automatic feed, record it directly: pick a resource if it is already listed, a callsign, the report's source (radio, GPS, or manual), an optional accuracy, and the coordinates. This creates an auditable, time-stamped observation and, if a listed resource was chosen, also updates that resource's current position on the map.

9. Data retention, backup and recovery

9.1 How the fire detection cache works

The FIRMS area API only answers a few days at a time per request. NexFiremap divides the world into a coverage grid (10 degree cells by default) and, for every combination of data source, cell and day, remembers whether it has already been fetched. When the viewport, time range or filters change, the server works out which combinations are still missing and queues only those; anything already cached is served straight from SQLite with no network call. Missing days are grouped into the largest chunks FIRMS will accept per request, stepping the chunk size down automatically if the API rejects a range. The most recent two days are treated as still filling in and are re-checked periodically (every 30 to 45 minutes depending on configuration, chapter 10.2), since satellites keep adding detections to them; anything older is treated as final and is never re-fetched once cached. A background job purges anything older than the retention window (30 days by default) once an hour. Zooming out far enough that a viewport would need many grid cells switches to a single whole-world request instead of one per cell.

In practice this means the first look at a region can take a few seconds to fetch, after which revisiting it is instant, and only the last day or two keep costing API calls.

9.2 How the basemap tile cache works

Every tile request is proxied through the server, saved to disk, and served from there on repeat visits, so panning back over an area already viewed costs no repeat download from NASA, FIRMS, or the tile provider. Concurrent requests for the same tile are combined into a single upstream fetch. Tiles are trusted for 30 days by default before being re-fetched, and the cache is capped at a configurable size (1 GB by default), evicting the oldest tiles first once exceeded. Tiles referenced by a complete offline AOI manifest (chapter 8.4) are pinned against both this age limit and this size eviction, so preparing an area for offline use is not undone by ordinary cache housekeeping later.

9.3 Backups

NexFiremap can back up its own database on a schedule (every 15 minutes by default) and on demand (verified backup, chapter 7.12). A backup is taken through SQLite's own safe online-backup mechanism, which works correctly even while the server keeps writing, then checked for internal consistency before being kept; a backup that fails that check is not kept. The most recent backups are retained (24 by default); older ones are pruned automatically. Backup management, including listing, verifying and downloading backups, is restricted to administrators.

9.4 Recovery

Create recovery copy materializes a separate, freshly verified database file from a chosen backup, checked for consistency both as the stored backup and again as the freshly made copy. Recovery never touches or replaces the database the server is currently running against; it always produces a new, separate file for download and further use elsewhere. Preserve the original failed database and its associated files for investigation rather than discarding them, and test a restored copy before relying on it. A drone imagery folder and any imported offline map sources are stored outside the database and are not included in a database backup; back those up separately (chapter 10.6).

9.5 Snapshots

A snapshot (chapter 7.10, create snapshot) freezes the full incident state, including every period, scenario, feature, resource, safety record, and the immutable results of anything since attached, under a name and a classification. Unlike a database backup, a snapshot is a versioned business record inside the database itself, meant for briefing and handover, not disaster recovery; take both where either matters. Comparing two snapshots, or a snapshot against the current live workspace, shows exactly what was added, removed, or changed, entity by entity.

9.6 Job output retention

Background analysis jobs (event detection, likelihood, burn scar, propagation, ensemble, validation, structure scans, orbit coverage) write their results, including any large rasters, to files kept for a configurable period (14 days by default) before being pruned; the most recent 200 job records are always kept regardless of age. A model run's outputs referenced from an attached scenario (chapter 7.7) should be preserved by keeping that scenario's snapshot rather than relying on job retention alone, since job files are not part of a snapshot or handover package.

11. Developer guide

This chapter covers the HTTP API, how to authenticate against it, how the background job queue works, how data is structured internally, how to feed data in from an external system, and how to set up the server for shared use on an incident LAN. It assumes familiarity with HTTP and JSON. 11.1 Architecture overview

NexFiremap is a single FastAPI application (nexfiremap/api.py) plus a vanilla-JavaScript frontend, backed by one SQLite database. There is no separate backend service and no build step. api.py itself is a composition root only: it wires up long-lived services in a lifespan function, adds one security middleware ahead of every route, and includes routers from nexfiremap/routes/. The route handlers themselves, roughly 150 of them, live one module per subject area under nexfiremap/routes/ (for example incidents.py, features.py, links.py, drone.py, backups.py); request and response body shapes are Pydantic models centralised in nexfiremap/schemas.py.

The offline incident-command data model lives in the nexfiremap/operations/ package (incidents and periods, scenarios, features, resources, cross-module links, packages/export-import, audit log), not in one file. External data formats are handled by stateless adapters in nexfiremap/ingest/, which only ever translate bytes into a shape an existing manager already accepts (chapter 11.7). Everything computationally expensive (clustering, rasters, imagery, physics propagation) runs through a background job queue (nexfiremap/jobs.py) in separate, idle-priority operating-system processes, never inline on a request (chapter 11.3).

One include-order rule is load-bearing, not cosmetic: in nexfiremap/routes/__init__.py, the links router must be included before the incidents router, because /api/operations/incidents/covering is a literal path that would otherwise be shadowed by /api/operations/incidents/{incident_id} under first-match-wins routing, and would answer a confusing 404 instead.

Several modules degrade gracefully rather than block startup: an optional dependency that fails to import (most often rasterio, which has real platform-specific install friction) disables just that feature, reported in GET /api/config's features object, rather than crashing the server. A route for a disabled feature answers 503 rather than 404, naming the missing dependency.

11.2 Authentication and permissions

By default (NEXFIREMAP_LAN_MODE unset or false) the server trusts every request from whoever can reach it, since it only listens on the loopback address. Everything in this section applies once LAN mode is enabled (chapter 3, chapter 11.6).

Sessions

Sessions are opaque bearer tokens held in server memory, not JSON Web Tokens; nothing survives a restart. Log in with:

curl -i -X POST http://127.0.0.1:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "<your admin password>"}'

On success the server sets an httponly, samesite cookie named nexfiremap_session (secure if TLS is configured) and returns a JSON body including a separate csrf token and an expires_at time. A script or external program calling the API must resend that cookie and also set header X-CSRF-Token to the returned csrf value on every request other than GET/HEAD/OPTIONS; a missing or wrong header is rejected with 403. All failure modes on login (unknown user, inactive account, wrong password) return the same generic 401, so a caller cannot use the response to enumerate valid usernames. Login is rate-limited to 10 attempts per 60 seconds per client. Sign out with POST /api/auth/logout.

Roles

The exact role set is viewer, field_editor, plans, safety, administrator, public; see chapter 3.3 for what each can read and write in plain terms. Enforcement happens once, in the security middleware, by matching the request path against a fixed table of substrings per role (for example, field_editor may write to any path containing /features, /resources, /field-imports, /position-reports or /assets). Because this is a coarse substring match rather than a per-route table, some routes that do not obviously belong to any role's listed tokens end up administrator-only by elimination (for example POST /api/events/detect and POST /api/operations/tactical-calculator); several routes additionally check administrator status explicitly inside the handler on top of the generic table, most notably every backup and settings route, and layer, webhook, and feed administration.

Machine-to-machine ingest

Three kinds of endpoint deliberately bypass the session/CSRF gate entirely and authenticate with their own per-resource token instead, since the caller is a device or another system, not a signed-in browser: position feed ingest (POST /api/feeds/positions/<source id>, header X-Feed-Token or query parameter token), the OsmAnd/Traccar tracker endpoint (same feed token, as a query parameter since the device cannot set headers), and mapped CAD webhook delivery (POST /api/ingest/webhook/<hook id>, header X-Webhook-Token or query parameter token). Each token is stored server-side only as a SHA-256 hash and shown in full exactly once, at creation or rotation; there is no way to retrieve a lost token, only to rotate it.

Public products

The public account role (chapter 3.3) is unrelated to a product's own classification field. A product or snapshot with classification: "public" becomes reachable without any session at all, through GET /api/public/products and GET /api/public/products/<id>/download; the classification value itself is the access control for those two routes.

Federated login (optional)

An installation can additionally accept OIDC or LDAP login (chapter 10.8) instead of, or alongside, local accounts; the local administrator account always keeps working regardless, as a break-glass path. A federated identity only ever mints the same kind of session described above; nothing downstream can tell a login was federated. OIDC login does not verify the identity token's own signature locally, relying instead on it having come directly from the provider's token endpoint over TLS, so the provider's certificate is the entire trust anchor; there is deliberately no way to disable that TLS check. LDAP authenticates a bind only; role comes from a configured mapping, not a group search, and an empty password is refused before any connection is opened, since LDAP otherwise treats that as an anonymous bind.

11.3 Background jobs

Anything expensive runs through one job queue rather than inline on a request. Worker processes run in a process pool (not threads, so numerically heavy code is not limited by Python's global interpreter lock) and are dropped to idle operating-system priority immediately after starting, so a running job only spends CPU cycles nothing else on the machine wants. Job rows live in SQLite with live progress, so status survives a server restart.

curl -s -X POST http://127.0.0.1:8000/api/jobs \
  -H "Content-Type: application/json" \
  -d '{"kind": "detect_events", "params": {"bbox": "11.4,48.0,11.8,48.3", "days": 14}}'
# {"job_id": 42}

curl -s http://127.0.0.1:8000/api/jobs/42
# {"id": 42, "kind": "detect_events", "status": "running", "progress": 40, ...}

curl -s http://127.0.0.1:8000/api/jobs/42/files/some_output.png -o output.png

Status moves through queued, running, and ends at done or error; a cancelled or server-interrupted job also ends at error with an explanatory message. GET /api/jobs?status=&kind=&limit= lists jobs, newest first. POST /api/jobs/<id>/cancel cancels a queued job promptly; a job already executing cannot be interrupted mid-step and finishes or times out instead. A job's own output files (rasters, GeoJSON) are fetched individually rather than inlined in the status response, since some are large.

Submitting a job directly through POST /api/jobs bypasses whatever validation the more specific domain route for that job kind would otherwise apply, so several job bodies re-check their own bounds internally (member counts, resolution, split counts) rather than trusting a caller to have gone through the normal route. Prefer the domain-specific route (for example POST /api/events/{id}/ensemble) over submitting a raw job kind directly unless there is a specific reason not to.

11.5 Data formations: how records are structured

"Formation" here means the shape data is organised into, and the rules that keep that shape trustworthy across time, re-runs and multiple installations. There are two formations to understand: the incident hierarchy itself, and how analytical results cross into it.

The incident hierarchy

Records nest in one fixed order. An incident (table incidents) has a name, an optional incident number, a status (active, contained, closed), a timezone, optional centre coordinates, notes, and a revision number. It contains operational periods (each with a name, start and end time, status draft/active/closed, and objectives), which contain plan scenarios (each with a name, kind primary/contingency/alternative/worst_case, status draft/approved/retired, description and assumptions). A tactical or observation feature belongs to a period and, usually, a scenario, or can attach directly to the incident with both left empty. Resources (crews, engines, aircraft) belong only to the incident, not to any one period or scenario. A feature is never hard-deleted: removing one sets its status to inactive and stamps a deletion time, so every id referenced elsewhere, including in an already-exported package, keeps resolving.

Revision control

Every mutable record (incident, period, scenario, resource, feature) carries an integer revision, starting at 1. Updating one requires sending back the expected_revision the caller last read. The server checks the current revision before writing and again as part of the write itself (UPDATE ... WHERE id = ? AND revision = ?), so a second writer racing in between cannot silently overwrite the first. A stale revision, or a write that loses the race, is rejected with HTTP 409 and a body shaped {"detail": "record changed since it was loaded", "code": "revision_conflict", "current": <the current record>}; reload the current record and retry against its revision rather than resending blind. Scenario approval treats expected_revision as optional, since approval is often triggered from a checklist view that is not tracking the scenario's own revision number.

Cross-module links: immutable snapshots, not live references

Fire events, model runs, alerts, drone assets, field imports, raw-detection windows and structures are all things that change identity over time: an event's clustering can be re-run and its numeric id is not stable across runs; a model run's arrival surface changes if the model is re-run with new weather; detections themselves are purged on the retention window. Because of this, anything from the analytical side of the application that gets attached to an incident is attached as a frozen snapshot, never as a live reference that could later point at something different or gone. POST /api/operations/incidents/{id}/links requires a non-empty snapshot object and refuses an empty one outright; the snapshot is capped at 256 KiB and is stamped with the time it was taken. Attaching the same (kind, ref_id) pair twice refreshes the existing link's snapshot rather than creating a duplicate. A link kind is one of event, model_run, alert, drone_asset, import, detection_window, or structure. Removing a link is a genuine, permanent delete, unlike a feature's soft delete, since a link is a statement about the incident's own record rather than a shared entity another record might still reference; its full content is preserved in the audit log regardless.

An incident's area of interest is a normal GeoJSON polygon (or a bounding box, which the server converts to one), stored on the incident itself and used by two things: the reverse lookup GET /api/operations/incidents/covering?lat=&lon=, which only ever matches incidents that actually have an area of interest drawn, never by distance from a centre point, and the per-position safety check that runs after every accepted vehicle position (chapter 11.7.2).

11.6 Setting up routing for a shared incident LAN

This section is for an authorised incident-system administrator preparing NexFiremap for more than one device. NexFiremap is not certified by the software itself; local command, security and GIS leads remain responsible for accepting a deployment and its data.

  1. Use a dedicated, patched command laptop and a trusted, incident-only local network.
  2. Set NEXFIREMAP_LAN_MODE=true, a unique admin password of at least 12 characters in NEXFIREMAP_ADMIN_PASSWORD, and a short NEXFIREMAP_SESSION_MINUTES.
  3. Configure both NEXFIREMAP_TLS_CERT_FILE and NEXFIREMAP_TLS_KEY_FILE. The certificate must name the address field devices will actually use. Install and verify its issuing certificate authority on every device before the briefing; never teach anyone to click through a certificate warning. If TLS is instead terminated at a separate, hardened reverse proxy, bind NexFiremap only to that proxy's own private interface.
  4. Start with an explicit non-loopback address, for example 
    python run.py --host 192.168.50.10
    Startup should show the LAN warning and an https:// URL.
  5. Sign in as admin, open Incident LAN accounts (chapter 3.4), and issue one named account per person with the least-privileged role that covers their job. Do not share the administrator account.
  6. Import and verify the area's map pack, create a verified backup, disconnect the wide-area network, reload two field devices, and confirm the map, incident data, drawing, products, sign-out and sign-in all still work. Every selected zoom level in the offline coverage check must read complete.
  7. For each approved vehicle gateway, create a position feed and transfer its one-time token through a protected provisioning process, never a shared briefing document or a browser bookmark; test rotating and revoking a token before relying on it.
  8. Confirm the drone desk's classification, retention and privacy procedure, and test a real nadir frame with known ground control before relying on suggested corners in the field.

During operations: keep the command server on protected power and watch the local-server pill; treat every stale observation and model warning as unresolved until a named operator updates or explicitly reviews it; create a snapshot at every operational-period change and before any handover; use the public-information template for anything released publicly, since every other product class contains command records; download verified backups to separate media, since a backup left only on the command laptop is not a recovery copy; and remember that the drone folder and any imported offline map sources live outside the database and are not covered by a database backup.

If someone cannot sign in, an administrator creates a replacement named account rather than disabling authentication or exposing the loopback-only mode to the network. If the administrator credential itself is lost, stop the server, set a new NEXFIREMAP_ADMIN_PASSWORD, and restart: the local admin password is rotated at startup without touching any incident data. Full detail, including database failure recovery and handover procedure, is in INCIDENT_LAN_RUNBOOK.md in this repository.

11.7 Feeding data in: standards interoperability

Chapter 8.7 describes this from an operator's point of view. This section is the wire-format detail needed to actually connect an external system. Every adapter lives in nexfiremap/ingest/, takes raw bytes plus a small amount of context, and returns a list of dicts already shaped to match either TelemetryManager.ingest (a position report), FieldImportManager.prepare (an overlay feature), or AlertManager (an alert). No adapter opens a network connection, touches the database, or reads a setting; it only parses. This is a deliberate architectural rule, not an accident: it means a new external format is always a new parser, never a new way to write to the database.

Cursor-on-Target (CoT) / TAK

XML <event> elements, CoT 2.0. a-* types (atoms, positions) become position reports; b-* types (bits: markers and shapes) become overlay features when NEXFIREMAP_COT_ACCEPT_FEATURES=true. Speed is read as m/s; altitude as metres above the WGS84 ellipsoid; CoT's "unknown" sentinel value on circular/linear error and altitude is treated as not present; a report at exactly 0,0 (no GPS lock) is skipped rather than stored as a real position. Post to POST /api/feeds/positions/<source id> with Content-Type: application/xml (or application/cot+xml) and header X-Feed-Token. NexFiremap can also stream this continuously to a listening TCP/UDP gateway (chapter 11.7.7), and can render an incident back out as CoT for a TAK client to poll, at GET /api/operations/incidents/{id}/cot.

NMEA 0183

Only RMC and GGA sentences are read; anything else is ignored. Coordinates are the raw ddmm.mmmm NMEA format, converted server-side. A checksum, if present, is validated; GGA carries no date, so date comes from an RMC sentence in the same payload, or from the server's own clock if none is present. Because NMEA carries no identity of its own, the request must supply a callsign: POST /api/feeds/positions/<source id>?callsign=Brush%2012 with Content-Type: text/plain and the raw sentences as the body.

MAVLink

Only message id 33 (GLOBAL_POSITION_INT) is decoded from raw MAVLink v1/v2 binary frames; there is no CRC or v2 signature verification, which is exactly why this path is expected to run only over the CoT gateway's own address-allowlisted, LAN-only listener (chapter 11.7.7), never exposed directly. Because a MAVLink frame carries only a boot-relative timestamp, the newest frame in a batch is anchored to the moment of receipt and earlier frames in the same batch are back-dated by their relative offset. A callsign must be supplied, the same as NMEA. Content-Type: application/x-mavlink.

Common Alerting Protocol (CAP)

OASIS CAP 1.2 XML. Only alerts with status="Actual" are treated as live; exercise, system, draft and test messages are skipped. A circle area is approximated as a 64-sided polygon; multiple areas combine into one multi-polygon. This adapter is not reachable through a public route: NexFiremap polls configured feeds itself (NEXFIREMAP_CAP_FEEDS, chapter 10.10) rather than accepting a pushed CAP document.

Shapefile

A ZIP bundle containing .shp, .dbf and, ideally, .prj, used through the ordinary field-observation import (chapter 8.5, POST .../field-imports/preview with format: "shp"). Only WGS84, ETRS89, Web Mercator and WGS84 UTM projections are recognised from a .prj file; anything else is refused by name rather than guessed, since a wrong guess on a projected coordinate system could place features a country away with no visible sign of the error. A bundle with no .prj file requires the caller to explicitly assume WGS84.

Mapped CAD JSON (webhook)

  -d '{
    "name": "CAD feed",
    "incident_id": "INC1",
    "source_id": "cad-1",
    "mapping": {
      "callsign": "$.unit.name",
      "latitude": "$.location.lat",
      "longitude": "$.location.lon",
      "observed_at": "$.timestamp"
    }
  }'

The mapping accepts only a dotted/indexed path ($.a.b[0].c), a literal string, or a literal with interpolated paths; there is no arithmetic, no conditional logic, and nothing resembling code evaluation, since a mapping language that could execute anything would turn every hook URL that ever leaks into a way to run code on the server. Mapping targets are restricted to the position fields themselves, so a mapping cannot inject arbitrary properties. If a payload arrives that the current mapping cannot translate, it is kept (not discarded) as a dead letter, retrievable with candidate field paths suggested automatically, via GET /api/webhooks/{hook_id}/failures, so the mapping can be corrected from what the vendor is actually sending rather than from documentation. The CAD system itself delivers to POST /api/ingest/webhook/{hook_id} with header X-Webhook-Token. Do not map external_id to something like a dispatch number that stays the same across a vehicle's whole call: NexFiremap treats a repeated external_id with different content as an error, so a moving vehicle would stop updating after its first position. Leave it unmapped unless the source system truly issues a unique id per message.

Live CoT/MAVLink gateway and MQTT bridge

For a source that streams continuously rather than making individual HTTP calls, NexFiremap can run a small TCP/UDP listener speaking CoT and, optionally, MAVLink (settings in chapter 10.9), or bridge to an MQTT broker (settings also in chapter 10.9, topic format topic=source_id:format[:callsign], formats json, cot, nmea, mavlink). Both are disabled by default and both are explicitly intended for a closed, physically controlled incident LAN only: the CoT/MAVLink listener has no authentication of its own beyond a source-address allowlist and a rate limit, and MQTT connects only over TLS, with no setting to relax that. Neither should ever be exposed to a network that is not fully trusted.

11.8 Testing

There is no pytest runner or shared configuration; each file under tests/ is a standalone script with its own main(), printing failures and returning a process exit code of 0 on success. Run one directly:

python tests\test_core.py

Or run every test file and stop at the first failure (PowerShell):

foreach ($f in Get-ChildItem tests\test_*.py) { python $f.FullName; if ($LASTEXITCODE -ne 0) { break } }

Most tests need no network access and no FIRMS key; HTTP is stubbed with httpx's mock transport. The imagery and terrain modules' STAC/DEM/weather-fetching code paths use pystac_client/rasterio, which have their own HTTP transport and so bypass that mock; those specific code paths were verified live against real data sources instead, as noted in the test files' own comments.

12.1 Glossary

TermMeaning
AOIArea of interest: the polygon or bounding box an incident is scoped to (chapter 11.5.3).
Anderson 13A standard set of 13 fuel models (grass, brush, timber litter, slash and so on) used by the Rothermel spread equation, from Hal Anderson's 1982 reference (GTR-INT-122).
CAPCommon Alerting Protocol, the standard format official public warnings are published in.
CoTCursor-on-Target, the position/marker XML format used by TAK (Team Awareness Kit) systems.
CSRF tokenA second token, separate from the session cookie, that a caller must echo back to prove a request came from a page that actually holds the session, not from a third-party site exploiting a signed-in browser.
dNBRDifferenced Normalized Burn Ratio: the pre-fire NBR minus the post-fire NBR, used to classify burn severity.
EnsembleMany spread-model runs sampling different plausible weather/fuel assumptions at once, then weighted by how well each matched what actually happened (chapter 6.8).
Fast marchingA shortest-path style method for solving how far something (here, fire) has spread by a given time, used instead of a continuous partial-differential-equation solve for lower implementation risk.
FRPFire Radiative Power, in megawatts: how much heat energy a detection's pixel is radiating, reported by the satellite sensor.
GeoJSONA JSON format for geographic features (points, lines, polygons plus properties); NexFiremap's API returns it for most spatial data.
IsochroneA line or band showing where fire is estimated to have reached by a given elapsed time.
MAVLinkA binary telemetry protocol common to drones and other unmanned vehicles.
MBTilesA single-file SQLite-based format for a set of map tiles, commonly used to distribute an offline basemap.
NBRNormalized Burn Ratio, a satellite-imagery index computed from near-infrared and shortwave-infrared bands, sensitive to vegetation and burn condition.
Probability-mass envelopeA contour drawn so that the area inside it holds a stated fraction (50/80/90 percent) of a raster's total likelihood, not a contour at a fixed density value (chapter 6.5).
ProvenanceThe recorded origin, timing, and stated limitations of a model result or a file, kept attached to it wherever it is used.
Revision conflictThe error returned when an edit was based on a record that has since changed (chapter 11.5.2).
Rothermel modelThe standard 1972 (Albini 1976-corrected) equation set for surface-fire spread rate, the physics core of NexFiremap's modelled-spread layer.
SnapshotAn immutable, named freeze of an incident's full state at a moment in time (chapter 9.5), distinct from a database backup (chapter 9.3).
Symbology profileWhich set of map symbols and colours tactical features are drawn with (a NexFiremap default, a German DV 102 profile, or a US ICS/NFPA profile), configurable per installation.
Tri-state observation modelTreating "a satellite confirmed fire here", "a satellite passed and confirmed no fire here", and "no satellite ever looked here" as three distinct kinds of evidence, rather than collapsing the second and third into "unknown" (chapter 6.3).
WMS / WMTSWeb Map Service / Web Map Tile Service: standard protocols for serving map imagery from a GIS server, which NexFiremap can add as a custom layer (chapter 4.4).

12.2 Data sources and licensing

Fire detections come from NASA FIRMS; near-real-time products are provisional and may later be revised. Orbital elements come from Celestrak. Sentinel-2, Landsat, the Copernicus digital elevation model and ESA WorldCover all come through the Microsoft Planetary Computer. Weather and historical cloud cover come from Open-Meteo. Industrial-source candidates and building footprints come from the OpenStreetMap Overpass API. Elevation tiles for the 3D view come from AWS Open Data terrain tiles. Independent geostationary fire confirmation, where configured, comes from the EUMETSAT Data Store. Place search is proxied to Nominatim under its own usage policy. Basemap tiles are © OpenStreetMap contributors and the respective tile providers listed in the basemap picker; attribution is preserved in the map's own attribution control.

OpenStreetMap data is licensed under the Open Database License (ODbL); the attribution already shown on the map covers displaying it. Redistributing the cached tiles or data themselves as a separate dataset, rather than running this server, would need to satisfy ODbL's share-alike terms on its own. NASA FIRMS data carries its own use policy (credit NASA/FIRMS, do not imply endorsement); this only matters if cached fire data itself is redistributed, not the code that fetches it. Copernicus/ESA sources and Open-Meteo are openly licensed for reuse with attribution, already credited above. None of this affects the licensing of NexFiremap's own code, which is MIT-licensed; it matters only when redistributing the data this project caches, separately from the software itself.

12.3 Troubleshooting

SymptomLikely cause and fix
Banner: add your NASA FIRMS map keyNo FIRMS_MAP_KEY is set. The map, basemaps and every other module still work; only satellite detections are unavailable until a key is added and the server restarted (chapter 2.3).
